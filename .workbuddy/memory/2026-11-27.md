**重要：项目里已有一套 structured_outputs 体系，不要另起炉灶。**
- `app/structured_outputs/`（schemas / parser / retry / response_format / examples）
- `app/services/structured_output_service.py`（`structured_output_service`，方法统一走 `_call_and_parse`）
- `app/api/v1/structured_outputs.py`（已有 /structured/intent、/rag-answer、/agent-plan）

我最初建的 `app/schemas/order_info.py`、`app/prompts/order_info_extract.py`、`app/utils/structured_output.py` 都是重复实现，已删除，改成接入既有体系。

### 落地内容

- `OrderInfoExtractOutput` 本来就在 `app/structured_outputs/schemas.py` 里（用户说的“已定义”）。只补了校验：空值字符串归一为 None、`phone_last4` 必须是 4 位数字、`model_validator(after)` 用实际字段重算 `missing_fields` / `has_required_info`（模型自报不可信）。
- Prompt：`ORDER_INFO_EXTRACT_STRUCTURED_PROMPT_V1`（prompt_id=`order_info_extract_structured`，变量 `user_question`，scenario=ECOMMERCE_CUSTOMER_SERVICE），写进 `app/prompts/structured.py`；registry 注册。
- Service：`StructuredOutputService.extract_order_info(user_question, model, llm_provider)`，temperature=0.1 + `build_json_object_response_format()` + `_call_and_parse`（内含解析失败自动修复重试）。
- API：`POST /api/v1/structured/order-info`，`OrderInfoExtractRequest{question, model}`，依赖 `get_current_user` + `get_llm_provider`，返回 `ApiResponse[OrderInfoExtractOutput]`。
- 测试：`tests/test_order_info_extract.py` 10 个离线用例（字段抽取、缺字段、JSON 模式、自报值纠正、修复重试、LLM 异常、空值归一、手机号校验、prompt 注册、API 返回）。

### 实测（glm-5.3-flash）

- “订单 10001，手机号尾号 8848” → `{order_id:"10001", phone_last4:"8848", has_required_info:true, missing_fields:[]}`
- “我的订单怎么还没发货” → 两个字段都 null，missing 两个
- “我是手机 13800138848 那个” → `phone_last4:"8848"`、`order_id:null`（没把手机号误当订单号）

## StructuredOutputService 支持 json_schema + 自动回退

- 四个方法（classify_intent / generate_rag_answer / plan_agent_task / extract_order_info）都加了 `use_json_schema: bool = False`，通过 `_build_response_format(schema, name, use_json_schema)` 选格式：True → `build_json_schema_response_format(schema=..., name=...)`，False → `build_json_object_response_format()`。name 用 task_name（intent_classification / rag_structured_answer / agent_plan / order_info_extract）。
- 回退收口在新增的 `_chat_with_format_fallback()`：仅当 `use_json_schema` 且 `is_json_schema_unsupported(exc)` 为真时，用 `request.model_copy(update={"response_format": json_object})` 重试一次，并打 `structured_output_json_schema_fallback` warning。
- 判定函数 `is_json_schema_unsupported()`：status_code 必须在 {400,404,422,501}，且 raw_error/message 里**同时**出现 response_format|json_schema 和 unsupported|not support|unknown parameter|invalid value。这样鉴权 400、schema 自己写错、500 都不会被误判成“不支持”。
- API：四个请求体都加了 `use_json_schema` 字段并透传。
- 测试：`tests/test_json_schema_response_format.py` 9 个用例（默认 json_object、schema 格式、name 正确、回退成功并断言第二次请求、未开启不回退、500 不回退、无关 400 不回退、helper 三态、API 透传）。

### 实测

- glm-5.3-flash **支持** json_schema：use_json_schema=true/false 返回一致且正确，日志无 fallback。
- deepseek-chat 未配 key（`LLMProviderConfigError: LLM API Key 未配置`），没实测。
- “不支持”场景只有单测覆盖（构造 400 + raw_error='response_format type json_schema is not supported'）。

## 结构化输出修复改为循环重试（STRUCTURED_OUTPUT_MAX_RETRIES）

- `app/core/config.py` 新增 `structured_output_max_retries: int = Field(default=1)`，`.env.example` 同步 `STRUCTURED_OUTPUT_MAX_RETRIES=1`。
- `app/structured_outputs/retry.py` 重写：`parse_or_repair_structured_output(..., max_retries: int | None = None)`，max_retries 为空时读 settings。循环 `range(retry_limit + 1)`：首次解析不占重试次数，失败后用上一次的文本+错误 detail 再发修复请求（`_request_repair` 抽出来复用 REPAIR_SYSTEM_PROMPT）。
- 次数用尽抛 `AppException(code=ErrorCode.STRUCTURED_OUTPUT_PARSE_FAILED(50016), status_code=500)`，data 带 schema / max_retries / attempts / detail；service 里原有的 `except StructuredOutputParseError` 分支保留成兜底（现在实际不会命中）。
- 测试：`tests/test_order_info_extract.py` 增加 `test_repair_retries_in_loop`、`test_retry_exhausted_raises_app_exception`，12 个用例全过。注意 FakeProvider 按 calls 索引取 contents，第 1 次调用取 index 0。

## ChatService 回答前加意图拦截（intent gate）

- `app/services/chat_service.py`：`chat_with_ai(request, db=None, redis=None, llm_provider=None)` 新增可注入 provider（便于离线测试），缓存命中判断仍放在意图识别之前。
- 顺序：cache → 取/建 provider → `classify_chat_intent()`（走 `structured_output_service.classify_intent`）→ `build_intent_gate_answer()` 命中则 `respond_with_intent_gate()` 直接返回，不调主模型。
- 规则：`intent=query_order and need_order_id` → `ASK_ORDER_ID_ANSWER`；`intent=human_service` → `TRANSFER_HUMAN_ANSWER`；其余继续普通 LLM Chat。
- 意图识别失败（AppException / LLMProviderError）只 `chat_intent_classify_failed` warning + 降级继续回答，不阻断主流程。
- 顺手抽出 `build_chat_response()` 和 `save_chat_messages()`，让固定话术路径也正常落库（completed）和写缓存；主路径 latency_ms 仍是 500。
- 测试：`tests/test_chat_intent_gate.py` 6 个离线用例（订单号缺失、转人工、有订单号继续走模型、其他意图、识别失败降级、session/trace 保留）。假 provider 用「系统提示词里是否含『意图识别』」区分意图请求与普通请求。
- 注意：意图识别是额外一次 LLM 调用，每个 chat 请求都会多一次往返；流式 `stream_chat_with_ai` 未接入。
